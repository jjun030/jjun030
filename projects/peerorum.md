# peerorum (피어오름)

**같은 학교·학과 학생끼리 스펙을 익명으로 비교하는 서비스**

`2026.07 ~ 2026.09` · 5인 팀 프로젝트 · 백엔드, 배포 담당 · 사용자 약 50명

Java 17 · Spring Boot 4.1 · Spring Data JPA · QueryDSL · Spring Security · MySQL · AWS EC2 · AWS RDS · Gemini API · React · TypeScript

[Backend 저장소](https://github.com/peerorum/peerorum-backend) · [Frontend 저장소](https://github.com/peerorum/peerorum-frontend)

---

## 문제

대학생은 자기 학점과 스펙이 같은 학교, 같은 학과 안에서 어느 정도인지 알 방법이 없습니다. 객관적인 지표가 없으니 "나는 어느 수준인가" 하는 막연한 불안이 생깁니다. peerorum은 이 불안에서 시작해, 같은 학교·학과 학생들이 서로의 스펙을 익명으로 비교할 수 있게 만든 서비스입니다.

## 내 역할

5명 팀에서 백엔드와 배포를 맡았습니다. 백엔드 저장소 115개 커밋 중 77개, 프론트엔드 저장소 100개 커밋 중 53개가 제 커밋입니다.

- 프로젝트 초기 설정과 익명 스펙 비교·회원 인증 백엔드 MVP
- 스펙 인증 API: 자격증, 대외활동, 학점, 어학 성적은 증빙 이미지로, 인턴과 수상은 별도 API로 검증
- Give to Get 열람 정책, 동적 검색, 전역 예외 처리
- 피드백 게시판 도메인, 관리자용 사용자 관리 API
- AWS EC2와 RDS 환경에 서비스 배포, 프론트엔드(Vercel)에서 EC2 백엔드로 요청을 넘기는 프록시 설정
- 프론트엔드 인증, 스펙 비교, 관리자 화면을 실제 API에 연결

GitHub Actions 배포 워크플로 작성과 소셜 로그인은 팀원이 맡았습니다.

## 핵심 결정

### 1. 증빙 검증을 유료 API 대신 Gemini Vision으로

자격증, 성적표 같은 증빙을 확인하려면 이미지에서 이름과 점수를 읽어야 했습니다. 처음에는 QNet 연동을 mock으로 만들어 두었지만, 유료로 알고 있었고 학생 팀이라 비용을 쓸 수 없었습니다. 그래서 Gemini Vision 무료 등급으로 증빙 이미지를 OCR하고, 제출자 이름과 입력한 문서 정보가 이미지와 맞는지 판정하도록 검증 방식을 하나로 통일했습니다.

- 응답 형식을 `responseMimeType: application/json`으로 고정하고, `{verified, reason}` JSON만 받도록 프롬프트를 설계했습니다.
- 모델이 JSON을 마크다운 코드블록으로 감싸 보내 파싱이 실패하는 문제가 있어, 코드블록을 벗겨 낸 뒤 파싱하도록 고쳤습니다.
- 인증에 실패하면 실패 사유(reason)를 사용자에게 보여 주도록 백엔드와 프론트를 함께 수정했습니다.

### 2. 인증한 사람만 남의 스펙을 보는 Give to Get 정책

익명 비교 서비스는 자기 정보는 내지 않고 남의 정보만 보는 사용자가 생기기 쉽습니다. 비교 API(`/api/comparison/**`) 앞에 인터셉터를 두어, 학교 인증이나 자격증, 대외활동 중 하나 이상을 인증한 사용자만 다른 사람의 스펙을 열람하도록 설계했습니다.

### 동적 검색

학교, 학과, 입학년도, 희망직무, 학점 범위를 사용자가 고른 조건만 붙여 검색하도록 QueryDSL `BooleanExpression`을 조합했습니다. 값이 없는 조건은 null을 반환해 쿼리에서 빠지기 때문에, 조건 조합마다 쿼리를 따로 만들지 않고 타입 안전하게 검색할 수 있습니다.

## 트러블슈팅 1: 인증 실패 항의의 진짜 원인

**상황**: 배포 후 테스터로부터 "AI 인증이 계속 안 된다"는 제보를 받았습니다.

**첫 대응**: 프롬프트의 판정 기준이 너무 엄격해서라고 보고 기준을 완화했습니다. 그래도 인증은 계속 실패했습니다.

**원인**: 계속 추적해 보니 프롬프트 문제가 아니었습니다. Gemini 무료 사용량을 모두 써서 API 호출 자체가 실패하고 있었습니다. 그런데 코드는 API 오류와 예외까지 모두 `verified=false`로 돌려주고, 이를 그대로 `REJECTED`(인증 거절)로 저장하고 있었습니다. 시스템 장애가 사용자에게는 "서류가 거절됨"으로 보였고, 저도 처음에는 판정 문제로 착각했습니다.

**조치**: Gemini API를 사용량 기반 유료 요금제로 전환해 인증 기능을 복구했습니다.

**배운 점**: 외부 API 실패와 비즈니스 판정 결과를 같은 값으로 표현하면 장애를 판정 문제로 오해하게 됩니다. 판정(승인/거절)과 시스템 오류는 다른 상태로 나누고, 오류는 재시도 대상으로 남기며, 사용량 초과 같은 응답은 따로 기록해 바로 알아챌 수 있어야 합니다. 무료 등급을 고른 결정에도 사용량 한도라는 운영 비용이 따른다는 점을 확인했습니다.

## 트러블슈팅 2: 사용자가 늘지 않는 문제

**상황**: 배포 후 사용자는 약 50명에서 더 늘지 않았습니다.

**판단**: 같은 기능을 계속 다듬기보다, peerorum이라는 이름과 지금까지 만든 기반을 가지고 다른 프로젝트로 전환하기로 했습니다.

## 결과

- AWS EC2와 RDS에 배포해 약 50명의 사용자를 대상으로 운영했습니다.
- 운영 중 외부 API 의존 구간의 장애 원인을 찾아 복구했습니다.

## 회고

- 외부 API에 기대는 기능은 실패를 "실패"로 드러내는 설계가 먼저라는 것을 배웠습니다.
